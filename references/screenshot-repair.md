# 普通商店截图整改：从审核意见到最终 PNG

适用场景：已有产品、定稿或审核意见，要保留整体风格并尽快替换有问题的画面。新项目也可在选定方向后使用这条生产路径。普通截图、App 预览视频、Header 和 Search Results 有各自的规则，先确认本轮对象。

## 1. 把审核意见翻成可验的条件

先看 App Review 给这个版本的原话、附图、设备和构建，再查当期官方指引，记录链接和核对日期。区分审核员指出的问题、Apple 对整套的要求和项目自己的视觉偏好。点名的图片先修，验收覆盖会送审的整组。并非所有拒审都能靠换图解决；如果是产品行为或审核员无法进入功能，先定位对应问题。

| 这类意见是什么意思 | 开工前怎样安排 | 怎样验收 |
| --- | --- | --- |
| 2.3.3：多数图没看出 App 正在使用 | 每个设备类型、每个有独立素材的本地化分开列页。为每张写出「用户正在做什么」「画面中哪里能证明」 | 只把能清楚辨认当前 App 的核心操作或真实结果的页计入实际使用。每组须严格过半，即总数为 N 时至少 floor(N/2)+1 张。按最终 PNG 重数，不能跨设备或语言凑数 |
| 加了标题、外壳或放大镜 | 先摆真实主画面，再决定说明放哪。设备外框是视觉选择 | 官方允许辅助文字、图片叠加；主功能、关键控件和结果必须仍看得清。孤立工具条、极小的 App 图、登录或启动页不能当作可靠的实际使用证据 |
| 2.3 准确性：界面、功能或数据与实际不同 | 对照送审构建的导航、图标、选中态和可到达的结果；选用有使用权的素材与虚构账户数据 | 区分 App 自带控件与海报注解。涉及额外购买时按 2.3.2 核对所展示项目的披露；官方没有统一角标样式。不得把某个产品的角标决定推广到其他产品 |

依据：[Apple 对 2.3.3 的专门说明与正反例](https://developer.apple.com/help/app-review/guideline-reference/2-3-3-screenshots)、[审核指南 2.3（含 2.3.2、2.3.9）](https://developer.apple.com/app-store/review/guidelines/#accurate-metadata)、[各设备截图规格](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications/)。竞品只供研究呈现手法。上述计数适用于普通截图，官方没规定要用设备框或指定屏占比。

给争议页留出余量。例如八张中，两张分别是「选择 → 结果」和「步骤 → 结果」的组合演示，可保守地先不计。八张至少需要五张明确的实际使用图。第三张若以完整真实编辑页为主体，放大镜只解释同一处变化，可说明计入的理由。若拿掉此页整组就不够，优先补一张能独立看懂的操作画面。有争议的页标为待判，先按不计入复算；低于门槛就重新取景或换页。把“感觉像截图”改写成具体记录，如「该页能看到打开的照片、已选中的裁剪工具和真实裁剪边界」。归类是制作方自查，审核决定以 Apple 为准。

每条反馈在项目现有清单中留一行，例如「多数图没看出 App 在用｜平板·目标语言·第 3 页｜旧图只有结果｜改为实际预览并显示已选中的工具｜原始采集、导出 PNG、该组复算」。遇到其他条款，改填该条款对应的原文、本版事实和复核方法。立项时盘点缺口，出代表样张时验证单页，交付前用最终 PNG 再查整组。

## 2. 先建网页母版，再倒推采集

1. 冻结已认可的代表 PNG、原文案、用户标出的保留区和本轮允许调整的页。用「语言 × 设备 × 页号」列交付矩阵；商店文案的语言数与实际独立截图组可能不同。受影响页、复用页、缺原件的页分开标。
2. 在 HTML/CSS 里先摆整套槽位，以真实比例的占位或已有原图出一张代表图。每张只填写自己的文案、素材和焦点。将公共背景色／渐变、标题字形与断行、框位、边框、内外圆角、阴影方向与透明度、卡间距和安全边距集中定义；设备或语言例外就近限定。同设备的所有页使用同一份外框组件。已有干净标题层可冻结使用，裁区须避开老卡片和阴影。
3. 顺序从外到内：画布 → 标题区 → 可选设备框 → 屏内安全区 → 内容卡 → 局部注解。屏内槽吃未套壳的截图，圆角裁切及阴影各有唯一负责层。不要把带旧壳、旧阴影的整张海报放进新框，再靠白块擦边。
4. 每个槽位先记可用宽高、关键内容边界和允许裁切的方向。屏内可用高度扣掉真实导航、工具区、边距和组间距后，再分给输入与结果。以源比例计算：等比适宽后的高度 = 槽宽 × 源高 ÷ 源宽。若上下两组，先保住主结果的可读高度，再分配输入区；若左右两栏，对齐外卡上下沿，各栏内部按内容排。填满的标准是主体用足可用区域、重点能看懂，同时分组仍可辨认。
5. 如果等比适配导致大片空白、字太小或按钮被切，依次调整原生取景／列数、样例长度与图文比、分组高度；必要时重采。真实 UI 保持比例。适用的留白包括系统安全区、卡间距和突出主功能的空间，不靠拉伸、复制条目或截掉确认按钮换取面积。

**一条可复用的采集任务描述：** 页号／目标设备与语言／输入来源／要执行的操作／必须可见的状态与焦点／完成信号／输出槽位。已有满足条件且版本相符的原件可直接用。没有原件先按槽位重建自有示例；缺当前版 UI 或真实处理结果的页保留待采集标记。

## 3. 制作能证明功能的素材，采集真实操作

| 画面要说明什么 | 内容源怎么做 | 哪一部分必须在 App 中取得 |
| --- | --- | --- |
| 多份输入变成一个结果 | 用自有网页生成一份连贯、有自然段落的聊天、清单或文章。照片服务于内容；按实际引擎要求留真实重叠、覆盖首尾，准备刚好能形成完整行列的有意义输入 | 将同批输入导入干净相册，按演示顺序选择，采真实编号与完整按钮，再运行产品拼接、取得预览或导出。核对首尾、顺序、段数及对应内容。海报添加的虚线仅说明分段；如果文案声称标出了真实接缝，坐标必须来自实际结果 |
| 关键步骤与最终结果 | 取当前版本指南中对应的关键步骤与插图，在网页按实际操作顺序编号；另一侧使用同主题的结果，保留可读比例 | 使用真正的指南界面或其可溯源原生片段；重排的成图标为流程演示。核对平台差异，例如手机的震动提示与平板的静置提示，以及插图内系统弹窗的语言 |
| 清理、修复前后有细微变化 | 制作自有列表／模拟商店页，使变化位置确实有纹理、亮暗边或文字附近的可见参照。先验证原图的目标真的存在 | 同一次输入送入实际功能，采已选中对应工具的画面与处理结果。用共同锚点将原图坐标换算到预览坐标；两镜片取同一内容区域、用同倍率，引线回指真实位置。缩小后还看不出差异就换取样点或素材重采 |
| 某个工具正在工作 | 选一个能露出工具和作用对象的示例，例如让待标注物、待打码字段避开浮动面板 | 在 App 里选中工具、施加操作、等待真实状态，再截整页。对照送审构建的导航、控件图标和选中态；面板遮住结果就调输入或滚动位置 |

iOS/iPadOS 有工程并获准动态采集时，优先复用现有 XC 脚本。典型顺序是安装目标构建或可对照的隔离宿主 → 设置设备／App 与系统语言、地区、外观、状态栏及样例数据 → 经真实入口操作 → 等待可访问性元素、选中态、处理完成或结果文件 → 用 XCUITest 附件或 `xcrun simctl io … screenshot` 取图。一个批次复用已构建的宿主，切场景时重置状态；同一模拟器不要同时跑两个会改变界面的任务。宿主调用真实逻辑须说明与送审构建的对应关系。没有源码或运行授权就使用可核实的现有截图，标出证据缺口。[素材与生产](material-production.md)

手机和平板共用品牌与示例语义，各自采集导航、选择器、工具栏或浮层。放大核对系统日期、相册、弹窗、通知与示例正文的语言。用截图中的原生区域做解释性拼版时，保留完整控件与背景边界，并能追溯到来源。真实整页存在系统语言混杂时优先切换系统环境重采。

## 4. 快速出第一张，然后并行扩展

- 在用户指定范围内，从已有真实原件或能立即采集的组合中选最容易暴露问题的一页；其余高风险组合缺什么就并行备什么，不阻塞首样，也不算已验证。用真实素材做一张最终规格 PNG，让用户看到整张和问题部位的放大图。例如放大镜若对着无纹理的空白，先换示例；继续调外框不会解决问题。用户只要求先看一张时，就以这一张定方向。
- 复用同一网页母版和语言文案。槽位尺寸确定后，示例内容、XC 采集准备和渲染可以并行；拿到原件即填回网页。基准已获确认的例行修正直接做，对会改变整个方向的选择再请用户确认。扩到其它设备／语言时先看原生布局差异最大和文字压力最大的一组。
- 按依赖只重跑受影响的部分：外框改动影响共享该母版的页；某工具的图标改动影响使用该状态的截图；只换某语示例则重采对应组合。缓存核对内容、裁区、母版及其引用资源、字体、版本和渲染环境的指纹。最终文件存在或修改时间较新都不足以证明可复用。
- 按具体缺口协作。网页／前端工具负责槽位和确定性排版，视觉设计技能可协助构图或阅读层次；它们输出可复用的框架／参数。ImageGen 适合自有示例内的照片、插画或需要创作的独立装饰，例如两组之间的小箭头。先给出显示尺寸、方向、光影、透明背景和保留区，单独生成，在真实母版按最终大小看过再冻结原件、透明裁边和哈希。简单线条、数值、文案用网页绘制。原生控件、选中编号、真实处理结果交给 App。具体协作技能都是可选项，按任务已有授权和可用能力选用。

## 5. 出 PNG 后验收，回源精修

用已有 [HTML 批量渲染和图像审计工具](tooling.md)。固定 viewport、DPR、字体和渲染路径；等待图片解码、字体加载以及页面自己的就绪条件。导出到候选目录，交付矩阵只收正式图。**检查对象是刚导出的 PNG**，网页预览通过后仍要做以下检查。

| 看哪一层 | 怎么判 | 失败改哪里 |
| --- | --- | --- |
| 文件与矩阵 | 对照预期语言、设备、页序，逐张解码；检查遗漏、多出、意外重复、尺寸、方向、位深和透明度。普通截图按当期 Apple 规格检查透明通道。区分渲染时使用 sRGB、PNG 有 sRGB 标记、嵌入 ICC 三件事 | 改导出参数、命名或批次清单。要求原样复用的文件核对字节哈希 |
| 整套缩略总览 | 并排看标题基线、框体、阴影、卡片间距和图文密度；遮住标题试读一眼，能否从画面识别功能？每组重新执行第 1 节的审核计数 | 多页一起漂移先改网页公共参数；仅单张失衡就改该页槽位／内容源 |
| 每张原尺寸与风险局部 | 逐张检查文字、系统语言和状态。放大圆角边缘、外壳上下、半透明阴影、选图编号、接缝、镜片、键盘／工具条附近。核实按钮完整、旧边无残影、镜片同点、注解确实指向对象 | 平边／双框回到裁切与遮罩层；工具遮住结果就重新取景或采集；看不出效果就换能证明功能的输入。修改后重出 PNG，不在成图上贴补丁 |
| 固定区与功能证据 | 同设备、同环境只比较声明固定的矩形；标题、外框及阴影与可变屏内分开。等尺寸锁定层可逐像素比；发生合法缩放时可测字面位置／墨迹重叠，并目检。说明容差依据，不能靠放大排除区掩盖差异。屏内检查原输入与真实输出及操作状态 | 先查字体、色彩、素材或环境指纹，再改发生误差的源层；复核受影响页及一张共享组件的对照页 |

验收结论分开写：哪些图已有真实操作证据，哪些是流程示意；各组实际使用页数；哪些 PNG 检查通过、哪些仍待确认。如果另有授权替换商店截图，再从 App Store Connect 回读每组设备槽位、顺序、处理状态及源文件校验值，排除旧图和重复图；单独记录是否重新送审以及 Apple 最终决定。素材交付、商店接收和审核通过是三个不同的结果。
