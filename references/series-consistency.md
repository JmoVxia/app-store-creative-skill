# 整套一致性与设备合成

首次构图就建立一份项目规范和「投放位置 × 设备 × 本地化 × 页序」矩阵，后续首样、批量和修订都从这里取参数。让相同层遵守同一规则，同时保留真实设备与 App 状态的差异；不把某个项目的尺寸、间隙或容差变成通用审美标准。

## 分清间隙属于哪一层

| 层 | 要确定的边界 | 一致性判断 |
| --- | --- | --- |
| 设备机身 | 官方框或通用容器、材质、硬件开孔、摄像头与外轮廓 | 同设备组复用同一冻结原件和放置参数；手机与平板分别定义 |
| 屏幕视口 | 机身原件的屏幕开口、圆角遮罩、截图等比映射 | 原件边界与显示边界对应，四角不漏图；额外展示间隙采用项目选定的零间隙或固定间隙规则 |
| 原生安全区 | 系统栏、导航、底部区域及原生控件避让 | 按真实设备／系统／语言核对，不能当作海报 padding 随意抹平 |
| App 编辑工作区 | 裁剪底色、图像显示区、工具面板、滚动视口、弹层背景 | 对应真实操作状态；深灰裁剪区、浮层变暗或正常滚动截断不等于套框留白 |
| 自编内容与说明卡 | 合成流程页的卡片、列宽、内距、段间距、文字首末行 | 共用相应组件与栅格；还要检查位图原件内部留白，不能只量外层 DOM |

先标明“铺满”“有间隙”指哪层，再将同设备整套的规则落实到该层。不同页面组确需不同卡片结构时，明确组件作用域；原生布局或功能状态的差异记录来源与可变区域。不要为了整齐而拉宽控件、补白真实工作区、遮住操作或伪造效果。

## 一个参数来源，覆盖所有组合

规范可以放在 `project.json.parameters`，也可以引用项目自己的配置；母版、内容页和导出器读取同一来源，不各存一套常量。按品牌、投放位置、设备、本地化、页面组和必要例外分层，明确覆盖顺序。完整维度见[参数维度目录](parameter-dimensions.md)，记录会影响本轮结果的项目：

| 参数组 | 需要保存的内容 |
| --- | --- |
| 坐标与作用域 | 单位、坐标原点、原件／设计／CSS／最终像素、DPR、转换关系，以及固定值、允许变化、项目选定容差和来源 |
| 机身素材 | 型号、方向、来源 URL／核对日期、原件尺寸、文件哈希与使用条件；显示比例、位置、层级和原件屏幕开口矩形 |
| 屏幕与遮罩 | 截图原尺寸及比例、裁区、等比映射、视口间隙、遮罩文件／哈希、alpha 或亮度语义、遮罩尺寸／位置与实际浏览器路径 |
| 系统与状态 | 系统栏来源、设备／语言／外观、硬件开孔由哪层负责、背景与高度、弹层时的真实变暗方式和范围 |
| 文字与栅格 | 字体及版本／哈希、字重、字号与下限、标题基线／字面边界、行高、断行、卡片上下沿、边距、列宽、间距、内距和联动计算 |
| 内容完整性 | 必须完整保留的控件、编号、选中态、结果首尾及其 ROI；滚动视口允许截断哪里，说明页哪些内容不得省略 |

矩阵每项指向实际输入、参数组、母版／渲染入口、预期规格、固定与可变区域和验证状态。首样阶段就检查所有组合是否都有这条路径，避免某语言复制旧成品、某设备另走遗留模板。已有合格输出可按依赖指纹与质量结果复用；文件存在或 mtime 较新只能用于调度，不能证明符合当前规范。

## 设备原件与屏幕合成

选择拟真 Apple 产品图时，按当期[Apple 营销规范](https://developer.apple.com/app-store/marketing/guidelines/)使用其提供、适合 App 支持设备的产品框，并从[Apple Design Resources](https://developer.apple.com/design/resources/#product-bezels)获取。核对相应使用条件，原件不自行改色、加阴影高光、裁切或变形；不要用 AI 或手绘模拟替代 Apple 硬件。通用内容容器可以自行设计或用 AI 提供独立艺术素材，但不要混入 Apple 特有硬件细节。

同设备冻结并引用同一选定机身素材；重新下载或生成属于新输入，先检查差异。iPhone 与 iPad 分别保留自己的几何、屏幕比例、状态栏和摄像头／开孔关系，不能把手机框拉宽为平板框，也不能在不同页面混用有岛、无岛或不同机型。

入槽前检查源图是否已包含旧机身、内框、圆角白底、阴影、状态栏、硬件开孔或额外 padding。发现套壳原件先回到干净来源，硬件开孔只由一处负责；不得在已合成成品外继续套新框。完整截图映射到对应屏幕开口时保持原比例，控件 ROI 参与检查；不要用 `cover` 或非等比拉伸悄悄补满。需要统一系统栏时，优先在采集阶段设定；复用原生系统栏须对应设备、语言与外观，并保留真实弹层状态。

屏幕矩形对齐不代表圆角遮罩正确。CSS `mask-mode` 初始为 `match-source`，普通图像源按 alpha 解释：无透明通道的黑白灰 PNG 不会因黑色区域而自动透明，可能使内容从屏幕四角漏出。按实际素材显式采用 `luminance`，或将遮罩派生为正确的 alpha 图；保留原件和派生关系，再用最终 PNG 查看四角、开孔及浅深底交界。[W3C CSS Masking：Mask Image Interpretation](https://www.w3.org/TR/css-masking-1/#the-mask-mode)

还要实测当前浏览器的本地资源路径：`file://` 下 CSS 遮罩可能因加载限制把屏内全部隐藏，而常规 DOM 检查仍通过。按[工具说明](tooling.md)检查请求失败及屏内原件映射；外部不漏图与内部内容正确必须同时满足。

## 在首样暴露批量风险

先用真实素材验证主叙事，再按矩阵选择能覆盖风险的组合：原生平板、最长文案或不同文字体系、深色与弹层、屏幕四角、两列说明与完整结果、贴近边缘的工具。按风险覆盖选择，不固定样张数量；用户指定只看一张时先交这一张，记录其余覆盖范围。

首样同时看整张、原尺寸和风险局部，确认以下关系成立后再扩展：

- 标题、机身与屏幕边界引用同一套参数；状态栏、开孔、圆角没有重复或残影。
- 说明列重排后文字和控件仍完整；结果列等比，原件内部留白也符合这类内容的规则。外卡上下对齐不能靠拉伸图片或裁掉末行获得。
- 实际使用画面仍能证明对应功能，真实状态差异已解释，固定层和可变层有明确区域。
- 全矩阵走同一生产流程，设备／语言差异通过参数或组件处理。重复生产及逐张验收按[分层验收](quality.md)，不能用总览缩略图或 DOM 无溢出代替成品核验。

用户已授权的规范内纠错直接执行并复核，不为每层增设审批。调整公共参数时只重新打开关联组件、组合与确认；保留其他已确认成果及历史证据。用户未决定的新审美取舍回到相关示意，脚本通过不代替用户确认。
